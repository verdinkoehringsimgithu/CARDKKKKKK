# 配置与扩展说明

## 一套规则的所有权

场景的 `CardTableDemo.configuration` 引用一份 `CardTableConfiguration`。启动时先校验，再将配置转换成纯 C# 的 `BoardRules` 与只读 `CardCatalog`，创建新的 `BoardEngine`。运行期间不轮询设计资产，停止后修改、下次启动应用。

卡牌定义资产是名称、分类、序号、默认属性与插画的唯一设计入口。`CardDefinitionData` 是不包含 Unity 对象的只读定义快照；`CardData` 是实例/存档 DTO，保留已解析静态字段以兼容版本 1 存档。带目录的引擎生成或读取时重新解析静态字段，实例 ID、翻面与当前属性独立保留。不要直接修改 Capture 返回的数据来操作游戏，它只是防御性副本。

## 配置一张新牌

1. 进入 `卡牌桌面 > 游戏规则配置 > 卡牌目录`，点击“新建卡牌定义并加入目录”。
2. 定义 ID 使用稳定技术标识，例如 `herb.mint`；卡牌名称填“薄荷”；堆叠分类填“药草”；排序序号填 10。
3. 初始实例属性可填写“品质 = 1”。插画先留空，之后把 Sprite 拖入卡面插画字段。
4. 回到初始桌面页，把该定义加入某个牌堆；相同分类规则下，它可以和同分类的其他定义同堆。也可以不加入初始桌面，只通过运行时发牌列表生成。
5. 点击“检查配置”和“保存配置资产”。运行后发牌列表会包含“薄荷”，实例属性从定义复制，多张牌互不共享可变属性。

一个定义可以在初始牌堆中引用多次，每次得到独立实例。定义 ID 大小写敏感，不能重复、不能有首尾空白。发布后改显示名称没有问题，修改 ID 需要迁移旧定义映射。技术 ID 不用于玩家文案。

默认发牌列表展示目录里的所有定义。它是桌面原型的调试/体验入口；正式玩法选定后，可由玩法命令决定何时生成卡牌。

## 三种堆叠方式

| 选项 | 判断依据 | 例子 |
|---|---|---|
| 相同分类 | Family 相同 | 薄荷与鼠尾草都属于“药草”，可以同堆 |
| 相同定义 | 定义 ID 相同 | 两张薄荷可以同堆，薄荷与鼠尾草分开 |
| 任意卡牌 | 不比较种类，仍检查容量与几何 | 不同类别可叠放 |

“允许堆叠”关闭后，每个堆只能一张。初始桌面与存档也遵守该限制，不会在加载时偷偷拆散或丢弃牌。修改该规则后，需把初始牌堆相应改成单张。

“生成重叠时合并兼容牌堆”只处理生成位置与现有牌堆重叠的情况；关闭后尝试自动找空位。“整理时合并附近兼容牌堆”控制整理动作，附近范围用吸附距离判定。二者都不关闭手动拖放合堆。

整堆拖动与拆出单张分别有权限。普通拖动对应整堆，Shift 拖动对应单张；若禁用整堆、保留单张，就用 Shift 拖动。两个权限都关时仍可选择卡牌，但不能移动。

## 初始桌面与几何

一项 `InitialPile` 对应一堆牌，位置是底牌左下角，以桌面左下为原点。牌列表从底到顶。堆占用高度为：

`卡牌高度 + (张数 - 1) × 堆内纵向错开`

默认三堆在 `(180,360)`、`(540,360)`、`(900,360)`，每堆从底到顶为序号 3、1、2。可以清空整个初始桌面，从空桌面开始；单个空牌堆没有意义，应删除该项。

桌面宽高、卡片尺寸与错开量同时驱动显示和几何判定。吸附距离控制拖放接近牌堆时的吸附范围；间距用于自动找空位及整理。增加单堆上限不会放宽边界，太高的堆仍不能放下。配置验证使用与实际引擎一致的 Restore 校验，不额外维护一套近似规则。

## 可选功能真正从编译中移除

“功能与资源”页分为两件事：勾选项决定这份配置允许什么；“应用功能裁剪到编译”决定当前构建平台实际包含什么实现。需要二者同时启用才可用。

例如不需要洗牌：取消“洗牌”，保存，再点击“应用功能裁剪到编译”。`CARDTABLE_DISABLE_SHUFFLE` 会使 `BoardEngine.Shuffle.cs` 的完整类分部实现与对应 UI 调用不参与编译。没有留下空方法或静默成功的占位调用。恢复时重新勾选并再次应用。

当前七个模块是翻面、排序、洗牌、堆内调序、抽牌、整理、存档。核心六组放在 `Core/Operations`，文件包含本模块独占辅助实现；存档模块在 `Unity/BoardSaveStore.cs`。删除某一个源文件前，先用对应符号裁剪，确保所有调用点一起排除；确实永远不用时再物理删除该文件和对应 `.meta`。不建议保留一大块注释后的旧实现，Git 已保存历史。

编译符号作用于当前平台的整个工程，多个配置不能同时拥有不同的二进制能力。工具仅管理 `CARDTABLE_DISABLE_` 的七个已知符号，保留项目其他符号。它不会在导入资产、打开配置窗口或启动游戏时自动改变编译设置。

## 换界面与资源

`Prefabs/CardTableView.prefab` 是完整桌面视图，`Prefabs/CardView.prefab` 是通用牌面。改布局优先编辑 Prefab 与组件序列化引用，避免重新在启动器里拼装 UI。场景使用真实的 Prefab 实例，配置引用在启动器中。编辑预览由 Editor 代码读取配置，运行视图没有 `ExecuteAlways`。

单张插画属于 `CardDefinition.Artwork`；通用卡框、卡背、桌面、字体、音效与背景音乐属于 `CardTableTheme`。这些引用可为空。美术目录保留 `Art/CardFaces`、`CardFrames`、`Table`、`Icons`、`Audio/SFX`、`Audio/Music`，用户已有的 `Art/Assets` 不会被覆盖或自动接入。

## 接入下一步玩法的边界

修改时沿着职责走，不要把所有逻辑塞回演示组件：

- 只改变数值、初始桌面、分类或现有策略：直接改配置资产。
- 新的可配置规则：在 `TableRuleSettings` 增字段，经 `ToRules` 传给 Core，在核心唯一规则入口中生效，再为窗口加中文编辑项。只展示真正实现的字段。
- 新的玩家操作：在命令层增加操作入口，按钮与快捷键共同调用；操作须由核心候选状态校验后提交。
- 新的展示或动画：改 View/Prefab，不在动画回调里修改模型归属。
- 配方、回合、委托或胜负：先确定规则及状态所有权，再接入玩法层。当前卡牌“属性”只是实例数据，尚未存在任何自动触发效果。

底层没有采用 ECS、通用反射效果图或任意脚本规则解释器；现有卡量与小团队更适合显式策略、只读定义和少量独立操作。最近空位与桌面整理使用有界候选/启发式，不能保证全局最优装箱。后续若真实数据暴露瓶颈，再替换相应查询或布局实现。

## 存档兼容

版本 1 文件格式继续保留。旧版默认牌使用 `archive.sample` 等 ID，同一 ID 下还有多个序号；迁移按“旧版定义 ID + 旧版序号”匹配，之后解析为新稳定 ID。

默认资产提供三类各序号 1～3。旧版发牌可能产生 4～9，读取这些档案前需新建对应定义，并填写旧 ID/序号映射后加入目录。未找到定义、改规则导致堆不兼容或几何越界时整体拒绝恢复，当前桌面保留。不要靠随便改旧档内容跳过验证。

改定义默认属性只影响新实例，读取旧档保留其当前属性；改名称、分类、序号按当前定义解析。改变规则或目录较大时，建议为新的规则配置另填存档文件名，避免多套规则共用一个保存槽。
